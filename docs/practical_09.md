# Практическая работа №9

## Модели Django связи и операции с базой данных через ORM

Дисциплина: Технологии разработки приложений на базе фреймворков.  
Проект: Система учета партий в настольные игры.  
Репозиторий: https://github.com/yahaosaka/framework_pr1.  
Образовательная организация, группа, ФИО и вариант заполняются студентом.

### Цель

Описать данные существующего проекта моделями Django, настроить связи
и миграции, перенести данные ПР7 и заменить ручной SQL в представлениях
на ORM с сохранением пользовательских сценариев.

### Доработка проекта

Созданы Game (название, пределы числа участников, жанр), Player (имя,
email), Match (игра, дата, длительность, победитель, статус) и
MatchPlayer (состав участников). Первичные ключи — BigAutoField.
Match ссылается на Game и победителя через ForeignKey с PROTECT.
Участники связаны через ManyToManyField и явную промежуточную модель;
пара «партия–игрок» уникальна. Удаление партии каскадно удаляет ее
участия, но не игроков. Связи имеют related_name для обратных запросов.

Миграции games/0001_initial, players/0001_initial и
matches/0001_initial созданы и применены. В моделях и базе закреплены
допустимый диапазон 2–6 игроков, положительная длительность и
согласованность статуса с наличием победителя. Сервисы дополнительно
проверяют уникальность участников, диапазон конкретной игры и
принадлежность победителя к составу партии.

Выбрана стратегия новой базы: миграции создают таблицы в db.sqlite3,
а исходная data/boardgames.sqlite сохраняется без изменений.
Команда import_pr7 читает источник в режиме read-only, проверяет
целостность и переносит ID и связи в одной транзакции. Порядок:
игры → игроки → партии → участники. Повторный запуск не создает
дубликатов. Результат: 6 игр, 5 игроков, 8 партий, 23 участия.
Ошибка некорректного состава или победителя откатывает весь перенос.

Представления games/views.py и matches/views.py переведены на ORM.
Сохранены каталог, карточки, подбор по числу игроков, история,
статистика, рейтинг и обработка 404. Добавлены поиск по названию и
жанру, фильтры партий по игре, статусу и периоду, безопасная
сортировка по разрешенным полям и Paginator по 5 записей.
Тег querystring сохраняет фильтры при переключении страниц.

Использованы all, get, filter, exclude, Q, order_by, values,
select_related, prefetch_related, annotate и aggregate с Count,
Sum, Avg, Min, Max. Карта более 15 ORM-выражений приведена в
docs/orm_queries.md. CRUD реализован в сервисах и проверяется
командой orm_demo: create → get → update → delete, затем откат
транзакции. Веб-формы записи не добавлялись: задача ПР9 — слой данных.
README обновлен: запуск, модели, импорт, запросы, тесты и выгрузка fixture.

### Проверка и результат

- python manage.py check — замечаний нет.
- python manage.py showmigrations — миграции games, players, matches
  отмечены [X].
- python manage.py makemigrations --check --dry-run — изменений нет.
- pytest — 64 теста пройдены, включая прежнюю предметную логику и
  новые проверки импорта, связей, ограничений, CRUD, фильтров,
  пагинации, пустой базы и 404.
- flake8 . --extend-exclude=venv — ошибок нет; для автоматически
  сгенерированных миграций отключен только контроль длины строк.
- Повторный import_pr7 — те же количества, источник неизменен.
- orm_demo — CRUD работает, временные изменения не остаются.

Тест карточки партии подтверждает два запроса: один с JOIN для
игры и победителя и один для участников. Статистика проверена
на исходном наборе: 8 партий, 7 завершенных, 760 минут,
7 побед, 23 участия; множественные JOIN не завышают рейтинг.
Старые SQL-модули сохранены для ПР7 и импорта, веб-слой их не вызывает.
